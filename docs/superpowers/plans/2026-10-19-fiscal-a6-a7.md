# Fiscal A6 / A7 — prontidão e dados fiscais só pelo backend

**Goal:** fechar os achados de segurança da auditoria fiscal Codex (19/10/2026):
- **A6:** membro da org consegue `UPDATE familias set can_invoice=true` (ou NCM, CSOSN…) direto pelo PostgREST — fabrica "OK" no semáforo ou muda fiscal sem validação/push.
- **A7:** sessão de suporte **somente leitura** com `is_admin()` escreve em `empresa_fiscal` (as policies não exigem `can_write_current_org()`).

**Architecture:** 1 migration, sem mudança de front/edge.
- A7: `alter policy` nas policies INSERT/UPDATE de `empresa_fiscal`, acrescentando `and (select public.can_write_current_org())` (mesmo predicado das policies de `familias`).
- A6: trigger `BEFORE INSERT OR UPDATE` em `familias` (`public.familias_proteger_fiscal()`, plpgsql, `security invoker`, `search_path=''`). Se `current_user` é `authenticated` ou `anon`: UPDATE que muda (IS DISTINCT FROM) qualquer coluna protegida, ou QUALQUER INSERT direto (Codex plano: `origem` tem DEFAULT 'nacional', então todo INSERT já chega com coluna protegida — INSERT em `familias` fica reservado ao backend; o front não faz nenhum) → `raise exception ... using errcode = '42501'`. Demais papéis (service_role das edges, owner de RPC `security definer`) passam intocados.
- Colunas protegidas: `can_invoice, can_invoice_causa, can_invoice_em, fiscal_sincronizado_em, ncm, cest, origem_nfe, fci, ex_tipi, tributacao_icms, tributacao_icms_regime, descricao_fiscal, unidade, origem`.

**Evidência de que nada legítimo quebra (levantada 19/10):**
- Front grava em `familias` só: título/descrição (`queries.ts:465/480`), `variacao_principal_codigo` (`:492`), atacado (`:972/980`), fotos/capas (`upload-imagens.ts`, `produtos-saldo.ts:557`). Nenhum INSERT direto. Nenhuma coluna protegida.
- RPCs `security invoker` que fazem UPDATE em `familias` (`confirmar_inventario`, `desfazer_nota_compra`, `importar_nota_compra`) só têm EXECUTE para `service_role`. As demais são `security definer`.
- Edges escrevem com `service_role`.

**Teste:** `supabase/tests/adr135_protecao_fiscal.sql` via `scripts/teste-sql-desfeito.py` (transação desfeita em prod), com fixture própria (lote + família sob perfil real), impersonando `authenticated` com `request.jwt.claims`:
1. UPDATE de `titulo_ml` → 1 linha (RLS ok, trigger deixa passar coluna livre).
2. UPDATE de `can_invoice`, `ncm`, `fiscal_sincronizado_em`, `origem` → 42501 cada.
3. INSERT de família por `authenticated` (com e sem colunas fiscais) → 42501.
4. Fora do papel `authenticated` (reset role) → UPDATE de `can_invoice` passa.
5. A7: `pg_policies` de `empresa_fiscal` INSERT/UPDATE contêm `can_write_current_org` no `with_check` (e no `qual` do UPDATE).
Prova de vermelho: rodar o teste sem a migration → falha.

**Docs:** emenda ADR-0135; `TASKS.md`; `docs/reference/modelo-de-dados.md` (nota do trigger).

**Entrega:** `supabase db push` (link antes), `npm run db:check`, preflight:static, Codex no diff, CI, ff na main. Sem deploy de edge.
